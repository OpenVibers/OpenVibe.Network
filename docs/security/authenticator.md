# Authenticator rollout (Part 1)

`mfa_enrollment` is an owner-only Console setting: `off` (default), `pilot` (the configured owner and `ovprobe_merge_keep`), or `all`. The deployment-only `NETWORK_MFA_PILOT=1` also enables just those two pilot accounts while the Console remains off for everyone else. Remove that environment flag to end the pilot. These flags control enrollment and display, never enforcement of an already enrolled factor. Missing encryption configuration fails closed for enrolled users; existing sessions continue unchanged. No site data is cleared.

Deploy prerequisite: `NETWORK_MFA_KEY`, 32 random bytes encoded as exactly 64 hexadecimal characters, in the Network service environment. Generate once on the host using a cryptographic random generator, append directly to `/etc/openvibe/network.env` with owner-only permissions and without terminal output. Do not replace an existing key. Back it up with the service's encrypted secrets; losing it loses authenticator secrets. Restart through the normal deploy. AES-256-GCM binds each encrypted secret to its account id; HKDF separates encryption and remembered-cookie signing keys. Never store this key in Console, git, logs or a command argument.

Enrollment requires the current password. A server-created 160-bit secret is rendered as a local QR (qrcode 1.5.4, MIT), plus a manual key, and expires after ten minutes until confirmed. OTPAuth 9.6.0 (MIT) verifies six digits, SHA-1/30 seconds, one adjacent step of clock tolerance. A locked account row serializes confirmation, TOTP counters and recovery use. Ten 80-bit recovery codes appear once and only their individually salted bcrypt cost-10 hashes persist. Pending sign-ins are random 256-bit HttpOnly, Secure, host-only cookies, hashed in storage, expire in five minutes, and are bound to the factor generation and password credential. They cannot be exchanged as sessions. Five failures across pending states block the account's factor for five minutes.

Remembered-browser cookies are HMAC signed with a separate derived key, random, HttpOnly, Secure, host-only and expire in 30 days. The database holds only their hashes and public ids. The security page can revoke each browser. Password reset, token revocation and factor removal revoke remembered browsers and pending sign-ins. Existing access/refresh sessions retain their behavior. Factor disabling requires a current unused code or recovery code.

Account export covers metadata for all four tables and excludes secret ciphertext, credential hashes, code hashes, token hashes and generation values. ADR-033 erases all four tables. Errors are generic and no codes or secrets are logged. API calls use JSON, rate limits and account-bound authorization; the cross-origin account hub carries its existing Bearer token.

Validation: `ov test mfa account-data security-session login-auto-continue`; full suite in CI. Production pilot: enroll the probe, complete a new password sign-in with a fresh authenticator step, consume one recovery code, start another password sign-in and confirm the same recovery code is refused. Disable the probe factor using another unused recovery code after checking, so unattended probe work is not locked out. Do not enroll the owner's account without their own authenticator.

Research: [OWASP MFA guidance](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html), [OTPAuth implementation](https://github.com/hectorm/otpauth), [RFC 6238](https://www.rfc-editor.org/rfc/rfc6238). A passkey (Part 2) will authenticate on Network's own origin when sign-in starts on another site. Step-up claims, stronger session management and factor-change notifications follow in Part 3; phone verification follows in Part 4.
