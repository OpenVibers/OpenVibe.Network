# Passkeys (Part 2)

Enrollment uses the existing default-off `mfa_enrollment` owner setting and `NETWORK_MFA_PILOT=1` pilot (configured owner and `ovprobe_merge_keep`). Leave general enrollment off pending the account-screen review. Existing keys remain usable and protect the password fallback even when enrollment is off. Existing sessions and site data are unchanged.

The relying party is **openvibe.network**. On Network itself the exact allowed origin is **https://openvibe.network**. Product origins are allowed through WebAuthn Related Origin Requests (below); credentials are never registered independently at product domains, and enrollment/removal stay on Network. Local cryptographic tests simulate both origins; a browser ceremony requires the HTTPS page.

The pinned MIT packages are `@simplewebauthn/server` 14.1.0 (Node >=22) and `@simplewebauthn/browser` 13.2.2. Browser modules are served locally at `/vendor/passkeys/`; there is no third-party script or attestation service. We require discoverable credentials, user presence and user verification and request no attestation. Each account has a random opaque WebAuthn user handle. Up to ten keys have names, creation/last-use dates and backup metadata. The login page supports native conditional mediation and an explicit button.

All new API routes under `/api/auth/passkeys` have a 30/minute address limit (the server-to-server related routes have a 120/minute per-client limit), JSON-only mutations, no-store responses, and same-origin browser checks. Registration and authentication challenges live five minutes and are consumed atomically. Invalid assertions count toward the existing five-attempt/five-minute account lockout. Credential counters and removals serialize on the account row. A password-pending ceremony is bound to its pending account and cannot switch to another person's credential.

Adding/removing a key requires the current password and, when any factor is already registered, a current authenticator/recovery code or a fresh passkey proof. The latter is single-use, lasts five minutes and is bound to the exact signed-in session. Adding/removing a key invalidates outstanding management challenges and remembered-browser cookies, without revoking existing sessions. Adding an authenticator to a passkey-only account also requires factor proof. First-factor registration issues ten hashed recovery codes once; existing authenticator recovery codes are retained. Password sign-in can use a passkey or an unused recovery code as its second factor. Removing the last factor removes its remaining recovery codes.

`0067_passkeys.sql` is expand-only. ADR-033 exports credential metadata, omitting public keys, opaque handles, challenges, bindings and hashes. Account deletion removes both new tables; session-wide revocation removes account-bound pending ceremonies. No codes, private keys or assertion bodies are logged. This part does not add the Part 3 session/step-up claims or notifications.

## Related origin requests (cross-site passkeys)

`GET https://openvibe.network/.well-known/webauthn` publishes `{ "origins": [...] }` with `Content-Type: application/json`. The list is generated from the live service manifests' `publicOrigin` (`exposure.publicSite: service`) plus a short reviewed alias list; customer/tenant hosts (`*.openvibe.website`, Host/Link subdomains), infrastructure hosts (`api.`, `auth.`, `ingest.`, `s3.`, `themes.`) and http/non-default ports are never listed. All approved `openvibe.*` registrable domains share the `openvibe` label; `openre.stream` and `open.shoes` are two more, inside the browsers' five-label limit. `server/webauthn-origins.js` is the single source.

A participating product's own server brokers the ceremony with its registered OAuth client (confidential clients only; public apps and node principals are refused):

- `POST /api/auth/passkeys/related/options` → `{ state, options }`. The exact `origin` must be both the client's registered redirect origin and on the published list, and a random browser binding (32+ URL-safe bytes, kept in the product's own `__Host-` cookie) is required. Purpose is `login` only.
- `POST /api/auth/passkeys/related/verify` → `{ result }`. Network verifies the assertion against the exact signed `origin` and RP ID `openvibe.network`, requires user verification and the account's own discoverable user handle, consumes the challenge atomically, applies the existing counter/lockout/account-state checks, and stores a single-use result bound to that client and origin.
- `POST /api/auth/passkeys/related/redeem` → the product's ordinary OAuth token pair (same issuer, verifier and audience rules as `/oauth/token`). The result is consumed once and cannot be redeemed by another client or origin. No Network session cookie or browser-held Network token is involved.

Refusals tested in `test/passkeys-related.test.js`: unpublished origin, an origin not registered to the calling client, a registered but unpublished origin, wrong client secret/public client, wrong purpose, missing/short browser binding, wrong binding, borrowed state on another origin, expiry, challenge and result replay, concurrent redemption (one winner), wrong client/origin redemption, wrong RP, non-UV flags, wrong user handle, a Network-origin assertion in the product flow, a merged user and a pending-password ceremony for another account. The iOS/Android-style virtual authenticator is the existing software ES256 helper; a browser ceremony is verified in HTTPS Chrome with a virtual authenticator during rollout.

Checks: `ov test passkeys-related passkeys mfa my-modules agent-schema user-owned-trust account-data`; the pipeline runs the complete suite. `test/helpers/passkey-authenticator.js` generates genuine ES256 attestations/assertions for the real verifier; it does not stub verification. Tests cover wrong origin/RP/UV/account, replay, expiration, password fallback, recovery replay, management proofs, removal, flag-off enforcement and export.

For Fable: account passkey registration/name, fresh-authentication controls, one-time recovery display, key list/removal, sign-in passkey button, and native conditional UI entry point. All additions use plain kit markup with no new CSS.
